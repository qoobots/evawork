# 写技能

## 概述

技能不是文档，是**可执行的指令**。判断一个技能好不好，唯一标准是：
**它有没有让行为发生了可观察的变化。**

**核心原则：技能也走 TDD。**

## 什么是技能

一个文件夹 + 一个 `SKILL.md`，里面写：
- **何时用**（description，决定它会不会被触发）
- **怎么做**（正文，可执行步骤）
- 可选：脚本、参考、模板

## 技能开发的 TDD 映射

| TDD | 技能 |
|---|---|
| 写失败测试 | **写下"没有这个技能时它会怎么错"**（基线） |
| 看着它失败 | 让同类任务跑一遍，**记录实际发生的错误** |
| 写最少实现 | 写能修正那个具体错误的最小正文 |
| 重构 | 消重、缩短、把大块挪进参考文件 |

⚠️ **没做过基线就写技能，等于闭着眼睛改**——你不知道它有没有用。

## 什么时候该造技能

**该造**：
- 同一类纠正说了**三次以上**
- 一段流程每次都要你重复交代
- 领域知识（写法、命令、约定）需要反复提醒

**不该造**（直接做更省事）：
- 只用一次的事 → 写进提示词就行
- 通用常识 → 不值得占技能位
- 现有技能改一下就够 → **改现有的，别 proliferate**

## 四类技能

| 类型 | 是什么 | 例 |
|---|---|---|
| **纪律型** | 规则与要求 | 完成前先验证 |
| **技法型** | 怎么做（how-to） | TDD 的红绿循环 |
| **模式型** | 心智模型 | 先问清再动手 |
| **参考型** | 文档／API 速查 | 命令清单 |

## 目录结构

```
skill-name/
  SKILL.md          ← 必需。正文保持短，细节按需引用
  references/       ← 按需读的参考（长文档、规范）
  scripts/          ← 可执行脚本（当黑盒用，先 --help）
  templates/        ← 输出模板
```

## SKILL.md 结构

```markdown
---
name: skill-name
description: **何时用**这句话要写成"用户说 X 时用它"——决定触发命中率。
---

# 技能名

## 何时用
（一句话 + 典型触发说法）

## 核心原则
（一句话，贯穿全文的那条）

## 步骤 / 清单
（编号，可执行；每条能回答"怎么算做到了"）

## 红旗
（看到就停：想法 vs 事实对照表）

## 常见借口
| 借口 | 事实 |
```

## description（最重要的字段）

它决定技能**会不会被用到**。写成触发条件，不是功能描述：

- ✅「用户说『帮我 review／看看有没有问题』时用它」
- ❌「提升代码质量的辅助技能」

再补上关键词覆盖：用户在中文场景**可能用的说法**都写进去
（"审查"／"评审"／"review"／"把关"）。

## Token 效率（关键）

技能正文每写一句都会被读进上下文。**所以**：

- 正文只放**决策点与判据**，细节挪进 `references/`
- 例子只保留**最能说明问题的那个**
- 与任务无关的内容一律不进技能
- ⚠️ 上游经验：SKILL.md 超过 ~500 行就该拆

## 技能被无视的常见原因

1. **语气太软**——全是"应该""建议"，没有判据
2. **太长**——重点被淹没
3. **没给可执行动作**（"要清晰" vs "函数不超过 50 行，超了就提取"）
4. **description 没写触发**——压根没被读
5. **和项目不符**——命令、路径、约定对不上
6. **与别的技能冲突**——两套规则打架，模型选了错的

## 给自己造漏洞（重要）

**规则最容易被"我有正当理由"绕过。** 写完一条规则，问自己：

> 我要是想跳过它，会找什么借口？

把那个借口**写进技能的"常见借口"表**，并在"红旗"里加上对应的"想法 vs 事实"。

示例：
- 规则："完成前必须验证"
- 我会想："就改了一点点，应该没问题"
- 写进表：| "就改一点点" | 一点点也要跑，因为上次就是"一点点"弄坏的 |

⚠️ **精神与字面之争**：模型会说"我理解规则的意图，这次情况特殊"。这时唯一的答案是
**同一句话**：规则就是规则，例外要人来批。

## 技能检查清单

- [ ] description 写的是**触发条件**（含中文用户真会说的说法）
- [ ] 做过**基线**（知道没有它时错在哪）
- [ ] 每条规则都有**可执行动作**与判据
- [ ] 有"常见借口"表（覆盖自己会想到的绕过理由）
- [ ] 有"红旗"表
- [ ] 正文 < 500 行，细节在 `references/`
- [ ] 引用的文件**都存在**
- [ ] 工具名/命令/路径与**本项目实际**一致
- [ ] 与其它技能**不冲突**（说清谁优先）
- [ ] 找一个同类任务**实测**过行为确实变了
- [ ] 附带 `LICENSE`／出处声明（如果是引入或改编别人的）

## 反模式

- ❌ **叙事式正文**（讲故事讲原理）→ 换成可执行步骤
- ❌ **多语言混杂稀释**（中英夹杂术语没统一）→ 统一术语
- ❌ **流程图里塞代码**→ 代码块单独放
- ❌ **泛化标签**（"工具类"）→ 用具体的触发说法
- ❌ **一次写 500 行再测试** → 先跑基线，写最小修正，再扩
