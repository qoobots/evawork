# 分支收尾

## 概述

代码写完了 ≠ 活干完了。**还剩一个决定：这份改动怎么回到主线？**

这个决定**不是你的**，是搭档的——所以要做的是**把选项摆清楚**，不是替他选。

**核心原则：合并是有代价的动作，该由人来决定。**

## 步骤 1：验证测试

```bash
<跑完整测试套>
```

读**完整输出**。有失败 → 先修，别带着红灯去谈合并。

⚠️ "改动很小，测试应该没问题" → 跑一次就知道了。

## 步骤 2：判断环境

- 这是 **git 仓库**吗？（决定用哪条路）
- 有**未提交**的改动吗？
- 有**未跟踪**的文件吗？
- 当前在哪个分支？

⚠️ 未提交/未跟踪的改动要先说清楚——**"我以为都提交了"是最常见的丢改动原因**。

## 步骤 3：确定基线分支

新工作通常要并回 `main`／`master`／`develop`。
先确认，别默认（合错分支比不合更糟）。

## 步骤 4：把选项摆给搭档

**不要自己选。** 四个选项，各自的代价说清：

| 选项 | 适合 | 代价 |
|---|---|---|
| **1. 本地合并** | 自己的分支、单机开发 | 直接进主线，不可逆（虽有回滚点） |
| **2. 推送 + 开 PR** | 多人协作、需要评审 | 需要远端与平台；PR 要等审 |
| **3. 保持原样** | 还想继续做、想留着对比 | 主线没有这份改动 |
| **4. 丢弃** | 做错了方向 | **改动不可恢复**（除非有回滚点/隔离副本） |

推荐哪个、为什么——给出建议，但**等对方点头**。

## 步骤 5：按选择执行

### 选项 1：本地合并

```bash
git checkout <基线分支>
git merge <工作分支>
```

合并后**再跑一次测试**（合并本身可能引入冲突解决错误）。

⚠️ 有冲突 → 如实说"有冲突，需要你决定怎么解"，**不要自己挑一个版本硬合**。

### 选项 2：推送 + 开 PR

```bash
git push -u origin <工作分支>
```

然后告诉搭档 PR 链接与**评审重点**（`requesting-code-review` 那套）。

### 选项 3：保持原样

明确说清：**改动还在分支上，主线没有它**。

### 选项 4：丢弃

⚠️ **这是唯一不可逆的选项。** 执行前必须：
1. 确认搭档**明确**要丢（不是"嗯都行"的默认）
2. 说清会丢什么（列出改动）
3. 问最后一次"确定？"

## 步骤 6：清理工作区

合并/推送/丢弃之后：

- 删掉临时分支/副本（隔离副本用 `isolate/abandon`）
- 清掉临时文件
- ⚠️ 清理**必须在确认合并成功之后**——先删后合就两头都没了

## 速查

```
1. 跑测试 → 必须绿（读完整输出）
2. 环境：git 仓库？未提交改动？当前分支？
3. 基线分支是哪个？
4. 摆四个选项 → 等人决定 ← 不要自己选
5. 执行：合并 / 开 PR / 保持 / 丢弃（丢弃要二次确认）
6. 清理（合并成功之后才做）
```

## 常见借口

| 借口 | 事实 |
|---|---|
| "就一个小改动，直接合了吧" | 合并进主线是**不可逆**的（对历史而言）。小改动照样该问 |
| "我以为已经推到远端了" | 检查再说。没推就是只在本地 |
| "先清理再合并，干净些" | 顺序反了。先合成功，再清理 |
| "合并冲突我随手解一下" | 冲突意味着**需要人判断**。把冲突内容摆出来让人选 |
| "PR 模板我随便填一下" | PR 是给人看的。写清"这次改了什么、为什么、怎么验证" |
| "丢弃的分支应该没人要" | **不要替别人判断**。列出来问 |

**与本项目的关系**：

- 如果这轮工作跑在**隔离副本**里（界面勾了「在副本里改」）：
  - 合并 = `isolate/apply`（**会自动留回滚点**，所以合这一步能撤）
  - 丢弃 = `isolate/abandon`（工作区从未被动过）
- 本项目用**回滚点**（TS-060）兜底：即使合回了，`checkpoint/undo` 还能撤
- 相关：`verification-before-completion`（合并前必须验证）、
  `requesting-code-review`（开 PR 时的评审）
