# 接收代码评审

## 概述

评审意见是**信息来源**，不是评分。收到之后的第一动作是**验证**，不是照改。

**核心原则：每一条意见在动手之前，先确认它技术上说得通。**

## 响应模式

```
收到意见
  │
  ├─ 不懂它指什么 ────────→ 问清楚（不要猜着改）
  ├─ 不同意它 ────────────→ 用技术理由反驳（带证据）
  └─ 同意 ────────────────→ 先核实问题真实存在，再改

三类都必须**明确说出来**（尤其是第 2、3 类）——闷头改或默默不做，
对方无从判断你是没看见还是不同意。
```

## 禁止的回应

| ❌ 禁止 | 为什么 |
|---|---|
| 不理解也不问，按自己的理解改 | 改出来的东西可能解决的不是那个问题 |
| 默默不改，也不说 | 对方以为你同意了下次还会提 |
| 嘴上说"好"，然后按原样留着 | 最坏的一种：双方都以为解决了 |
| "这不行"但说不出为什么 | 反驳要有理由，没理由的否定等于拒绝协作 |
| 顺手做计划外的"改进" | 评审里混进自己的主意，对方无法分辨 |

## 处理含糊的意见

意见含糊时**先问**，一次问一个：

- "你说的 X，是指 A 还是 B？"
- "能举个具体例子吗？"
- "这个改动会影响哪些调用方？"

⚠️ **别把含糊当成小改动直接动手**——含糊通常意味着
"对方不确定自己说的是不是对的"，你猜着改大概率白做。

## 按来源区分处理

### 来自人（你的搭档）

- 他的**意图**优先于技术细节。他要的是效果，不是特定的实现方式
- 他可能不知道某个技术约束 → **要解释，但不要用术语堆砌**
- 他的偏好（比如"我们项目里都这么写"）应当被尊重

### 来自外部评审（工具/子代理/人）

⚠️ **外部评审会给出错误的意见**，尤其是：
- 不知道你的项目约定（命名、风格、目录）
- 不了解你为什么这么设计
- 只看 diff 就断言"这是 bug"

**处理方式**：先验证 → 对的改，错的**用证据反驳**。

## YAGNI 检查

评审说"这里应该加个 X"时，先问：

> 这个功能现在有人用吗？**谁会用？用的时候会怎样？**

答不上来 → **现在不做**。记进"将来可能要做"的清单。

⚠️ "加上去又不碍事"是错的——**每一行代码都要有人维护**。
将来真的需要时再加，那时你会更清楚它该长什么样。

## 实施顺序

收到一堆意见时，**先分类再动手**：

1. **必须改**（真 bug / 安全问题 / 明确的需求偏差）
2. **应该改**（可维护性、明确的坏味道）
3. **可选**（风格偏好、"顺手优化"）
4. **不做**（YAGNI / 技术上不成立 / 与你的判断冲突且无大碍）

⚠️ **一次全改会让评审的人无法判断你到底改了什么**。
按类别分批改，每批改完跑测试。

## 什么时候该反驳

**要反驳的情况**：
- 意见技术上不成立（附上你验证过的证据）
- 改了会引入更大的问题
- 属于个人偏好，不是缺陷
- 会破坏别的约定（说清是哪个约定、哪里写着的）
- 改动成本远超收益

**怎么反驳**：
1. **承认对方关心的问题是对的**
2. 给出技术理由
3. 给出证据（测试、数据、代码位置）
4. 提出替代方案（如果有）

示例：
> 你说的超时问题我同意存在。但改成 3 秒重试解决不了根因——
> 问题在连接池被长期占着（见 `pool.ts:88`）。我用超时只加了一个症状。
> 根因修法是给查询加索引（见附件的耗时分析，从 2.3s 降到 80ms）。
> 你更希望走哪条？

⚠️ **不要用"我觉得"当理由**——要拿证据说话。

## 承认正确的意见

对的方向要**明确承认**，不要用"嗯"敷衍：

> 对，这个问题确实存在。我改。

⚠️ 犹豫了半天才承认，对方会认为你在敷衍。

## 优雅地纠正自己的反驳

如果你后来发现自己反驳错了：

> 我之前判断错了 —— 你说的确实是我引入的。已改。

⚠️ **不要为了面子硬撑**。承认判断错误是专业性的表现，不是丢脸。

## 常见错误

| 错误 | 后果 |
|---|---|
| 全部照改 | 引入新问题，且评审的人无法分辨哪些是有意为之 |
| 全部不改也不说 | 对方以为你放弃了，会一直提同样的意见 |
| 改一半 | 一半一半最糟：既没解决，又动了不该动的 |
| 把意见当成命令 | 意见是判断，不是命令——但要**认真验证**再反驳 |

## 真实例子

**❌ 差**：
> 评审：这里可能有并发问题。
> 你：（直接加了个锁）

→ 没搞清是什么并发问题，加的锁可能解决不了、也可能加了死锁。

**✅ 好**：
> 评审：这里可能有并发问题。
> 你：指的是 `counter` 的读-改-写不是原子的吗？我加个并发用例复现一下。
> （写用例 → 确实复现了）
> 你：复现了，是非原子操作。我在读-改-写上加了锁（`counter.ts:42`），
> 并发用例现在稳定通过。

**✅ 反驳**：
> 评审：这里应该加个缓存。
> 你：问了下实际场景，这个接口每次请求的参数都不一样，缓存命中率接近 0，
> 而缓存一致性又要加一层失效逻辑。建议先不做，等出现重复查询再说。
