# 完成前先验证

## 概述

**核心原则：证据先于断言，永远如此。**

违反它的字面，就是违反它的精神。

## 铁律

```
没有新鲜的验证证据，就不许宣称完成
```

**"刚才跑过"不算**——验证命令必须**在当前这一轮里跑过**，输出必须是你亲眼看到的那一份。
会话早期跑过一次、或者"应该没问题"，都不能作为依据。

## 闸门（五步）

在说出任何结论或表示满意之前，按顺序走完：

1. **确定**：哪条命令能证明这件事？——想不出命令，说明这个结论**无法验证**，那就别说它成立
2. **跑**：完整执行（新跑一次，不要用旧输出、不要只跑一部分）
3. **读**：读**完整**输出，看退出码，数失败数（不是只看最后一行）
4. **判**：输出支持这个结论吗？
   - 不支持 → 说出真实状态（"跑了一遍，3 个失败"），不要粉饰
   - 支持 → 带着证据说结论（"34/34 通过"）
5. **然后**才说结论

跳过任何一步 = 在撒谎，不是在验证。

## 常见失败对照表

| 结论 | 需要什么证据 | 不算证据 |
|---|---|---|
| 测试通过 | 测试命令输出：0 失败 | 上一次跑的、"应该能过" |
| 检查无错 | 检查工具输出：0 错误 | 只查了一部分、外推 |
| 构建成功 | 构建命令：退出码 0 | 检查通过了、日志看着对 |
| bug 修好了 | 重跑**原始症状**的用例：通过 | 代码改了，假定修好了 |
| 回归测试有效 | 验证过红→绿 | 跑过一次就通过 |
| 子代理做完了 | 看版本控制的 diff | 子代理说"成功了" |
| 需求满足了 | 逐条对照清单 | 测试过了 |

## 红旗信号——看到就停下

- 用了"应该""大概""看起来"
- 验证之前就表达满意（"好了！""搞定！""完美！"）
- 没验证就要提交／推送／开 PR
- 相信子代理的成功报告
- 只做了一部分验证就下结论
- 心想"就这一次"
- 累了，想赶紧收工
- **任何暗示成功的措辞，而你并没有跑过验证**

## 合理化借口 vs 事实

| 借口 | 事实 |
|---|---|
| "现在应该能行了吧" | 去跑验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "检查都过了" | 检查工具 ≠ 编译器 |
| "子代理说成功了" | 自己独立验证 |
| "我太累了" | 累不是理由 |
| "检查一部分就够了" | 一部分证明不了任何事 |
| "换个说法就不算违反规则了" | 精神胜过字面 |

## 关键模式

**测试**
```
✅ [跑测试命令] [看到：34/34 通过] → "全部测试通过"
❌ "现在应该能过" / "看起来对"
```

**回归测试（TDD 红→绿）**
```
✅ 写用例 → 跑（通过）→ 回退修复 → 跑（**必须失败**）→ 恢复修复 → 跑（通过）
❌ "我写了回归测试"（没做红绿验证）
```

**构建**
```
✅ [跑构建] [看到：exit 0] → "构建通过"
❌ "检查通过了"（检查不编译）
```

**需求**
```
✅ 重读计划 → 列清单 → 逐条验证 → 报告缺口或完成
❌ "测试过了，这一阶段完成"
```

**子代理**
```
✅ 子代理报告成功 → 看 diff → 验证改动 → 报告真实状态
❌ 相信报告
```

## 何时应用

**永远在下列时机之前**：

- 任何形式的成功／完成声明
- 任何表示满意的措辞
- 提交代码、开 PR、宣布任务完成
- 转到下一个任务之前
- 把工作交给子代理之前

**规则覆盖**：字面说法、改写说法、同义表达、以及**任何暗示完成或正确的表述**。

---

**工具提示**：本项目里"跑验证"就是用 `run_command` 执行真实命令，然后**读它的完整输出**。
不要因为输出太长只看最后一行——失败往往在中间。

**一个常见坑**：改完代码立刻"顺手"提交。提交前必须重跑一次验证：上一次跑的是**改动前**的代码，
它证明不了改动后还对。
