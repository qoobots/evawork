# 技能使用指南

## 这个技能的作用

系统提示里已经列出了可用技能（名字 + 一句话摘要 + 触发条件）。
**这个技能负责的是"别漏步骤"**：动手之前先扫一遍清单，判断该用哪些、按什么顺序。

## 核心规则

**如果某个技能与当前任务相关，先把它读出来（`load_skill`）再动手。**

"相关"的判断标准是宽松的：哪怕只有一点可能相关，也值得读——
读一份技能的成本远低于漏掉它带来的返工。

⚠️ 但也不必**过度触发**：
- 一次任务通常只需要 1-3 个技能，不是全部十几��
- 与当前任务完全无关的技能不要读（白占上下文）
- 拿不准就问用户："这个任务要不要按 TDD + 先写计划来做？"

## 技能之间的优先关系

**流程类技能先于实现类技能。** 顺序大致是：

```
① 头脑风暴/澄清   → 搞清楚要什么（brainstorming）
② 写计划          → 搞清楚怎么做（writing-plans）
③ 隔离            → 在副本里干活，别弄脏工作区（using-git-worktrees）
④ 实现            → TDD 写码（test-driven-development）
⑤ 评审            → 派子代理互查（requesting-code-review / subagent-driven-development）
⑥ 验证            → 完成前拿证据（verification-before-completion）
⑦ 收尾            → 合并/开 PR/保留（finishing-a-development-branch）
```

**遇到问题时的分支**：
- 报错了、结果不对 → `systematic-debugging`（先找根因，别碰运气）
- 要重构 → `refactor` 纪律 + TDD
- Git 操作 → `git-workflow`（破坏性命令前必须确认）

## 一条更实用的经验

**如果你正要做一个有明确顺序、超过三步的改动，先写计划。**

不是所有任务都要走全流程。判断：
- **小改动**（1 个文件、有明确目标）→ 直接改，但要 TDD + 验证
- **多文件、有设计取舍** → 先写计划
- **不确定要做什么** → 先 brainstorming，别猜着做

## 什么时候该停下来问人

以下情况**不要自己决定**，问用户：

- 需求含糊（"帮我优化一下"到底优化什么）
- 要做**破坏性操作**（删文件、reset、清空、覆盖）
- 涉及**对外提交**（推送、开 PR、发布）
- 方案有**明显取舍**且你无法判断哪个更合适
- 你发现**前提是错的**（比如发现工作区不是仓库）

## 关于强制语气

⚠️ 上游这个技能原文写得非常强硬（"哪怕 1% 可能相关就必须调用"、
"这不是可以商量"）。**本项目刻意没有采用那种语气**，原因有二：

1. 本项目走 OpenAI 兼容通道，通篇 MUST 式指令**不一定被遵守**，
   反而像在施压
2. 更重要的是：**技能的价值在于它被用对，而不是被强制触发**。
   逼模型"什么都往技能上套"会让它选错技能、写不必要的计划，
   反而更慢更差

所以这里的立场是：**该用就用，但用对**。读完一个技能觉得不适用，
**说出来并说明理由**，比硬套上去有价值得多。

## 与本项目的关系

- 技能清单在系统提示的 `skills` 一节（名字 + 摘要 + 触发词）
- 读全文用 `load_skill`（不要把全文塞进上下文）
- 本项目另有 13 个自撰技能（文档协作、代码审查、调试纪律、视觉风格等），
  与 Superpowers 系列**互补而非替代**
- 相关：`writing-skills`（想造新技能时用它）
