# 头脑风暴

## 建立共识

头脑风暴的产出，是**你的搭档能认出来并纠正的**一份理解，而不是一堆你自认为明白的东西。

1. **发现意图**：从请求和上下文里找出**想达成的结果**、**给谁用**、**什么算成功**。
   缺这些就**先问一个聚焦的问题**（关于目的或用途），**再**提功能或方案。
   知道这是哪类应用，不等于知道搭档为什么想要它。
   补齐缺失的信息**不等于**要他再授权一次。

2. **把你的理解写回去**：用一小段话总结**预期结果、关键约束、成功标准**，让搭档能评估。
   **把他说过的**和**你假设的**分开。邀请他纠正，在把这段当作设计依据之前把他的意见吸收进去。

3. **把意图带进设计**：把达成共识的理解**保留在所选路径的设计产物里**——
   架构类写进书面规格，有界类/探针类写进对话里的设计与探针。
   拿这个理解去检查你提的每个功能与技术选择。

请求里已经给了目的和约束时，**把你的理解复述一遍**就行，别再问一遍。

> **硬门（HARD-GATE）**
>
> 在做任何实现动作之前——包括调用实现类技能、写产品代码、脚手架、
> 安装产品依赖、创建外部项目——先完成所选路径的前置条件：
>
> - **探针**：搭档认可那个问题与探针方案
> - **有界**：搭档认可对话里那份简短设计
> - **架构**：搭档评审并认可**书面规格**，然后再评审**书面实现计划**并选执行方式
>
> **一次回复只批准实际呈现的那个阶段。** 认可一个想法或功能范围，
> **不等于**认可还不存在的产物。从最早未完成的阶段接着走；
> 不要把一次批准变成"跳过这条路径其余部分"的许可。
> 前置条件未完成时，**只读的项目探索是允许的**。

## 三条路径

**在问第一个问题之前，先分类，并把分类说出来**——
"看起来这属于有界改动，所以我会在对话里给一份简短设计，而不是写规格"——
这样你的搭档才能推翻你的判断。

| 路径 | 是什么 | 产出 |
|---|---|---|
| **探针（Spike）** | 可行性问题（"能不能…""可行吗""糙一点也行"）。产出是**答案**，不是要保留的代码 | 说清问题 + 你打算怎么试（2-3 句），得到点头，然后**以尽量低的成本**去试。**无设计文档、无规格**。把结论报成**建议**；做出来的东西**标注为一次性** |
| **有界（Bounded）** | 对**这个仓库里已有代码**的、范围清楚的改动：一个开关、一个小端点、一个文件的修复 | 问关键问题 → 在对话里给**简短设计**（几句到几段）→ **停下**。搭档明确说"可以"之后才开始实现。**无规格文件、无计划文档** |
| **架构（Architectural）** | 新项目、新子系统、改变组件关系或对外接口的改动 | 走全流程：问问题 → 提方案 → 分段设计 → 书面规格 → 转 `writing-plans` |

**判定"有界"的门槛**：不是"我熟悉这类应用"，而是**你要改的那条流程已经存在于这个仓库里、可读**。
没有既有流程可改，就不是有界。

**两条路之间拿不准时，走更重的那条。**
**棘轮是单向的**：任务中途发现隐藏的复杂度 → **升级**路径（停下、说出来、往上走）。
**没有任何东西会在任务中途降级。**

## 反模式："太简单了不用设计"

每条路径都要搭档认可相应设计之后才能实现。
有界改动可能只需要对话里两句话；一个全新的待办项目是架构级的，
需要书面规格与计划交接。**产物规模随路径缩放，但那条路径的评审一个都不能少。**

## 红旗

| 想法 | 事实 |
|---|---|
| "太简单了，不用设计" | 按路径来：有界改动给对话里的简短设计，架构改动给书面规格与计划交接 |
| "我定性为有界，就可以跳过规格" | **想找个标签来跳过工作，本身就是拿不准**——走更重的那条 |
| "有界且设计显而易见，我边等他们看边开始" | 门是**批准**，不是设计的长短。呈现完就**停下**，听到"可以"再动 |
| "我熟悉这类应用所以是有界" | 有界衡量的是**仓库**，不是你的熟悉度。新项目没有既有流程，是架构级 |
| "探针跑通了，代码就留下吧" | 探针的产出是答案。保留代码是**新需求**——重新分类 |
| "它变大了，但快做完了，不用重新分类" | 隐藏复杂度会中途升级路径。停下来说出来 |
| "他们认可了探针，后续改动也算认可了" | 每个任务有自己的分类与批准 |

## 清单

先分类、说出路径，然后为该路径的每一项建一个任务，按序完成。

**探针：**
1. **探索项目上下文** —— 足够支撑探针方案
2. **呈现问题 + 探针方案** —— 2-3 句
3. **得到批准** —— 点头即可
4. **调查** —— 在保证正确性的前提下尽量省
5. **报告结论** —— 给**建议**；做出来的东西标注为一次性

**有界：**
1. **探索项目上下文** —— 看文件、文档、最近提交
2. **问关键问题** —— 一次一个
3. **在对话里给简短设计** —— 做法、动哪些文件、怎么测
4. **得到批准** —— **停下**等明确同意；边呈现边开工就是跳过门
5. **实现** —— 走正常开发流程（**TDD 适用**）；**不写计划文档**

**架构：**
1. **探索项目上下文** —— 看文件、文档、最近提交
2. **问关键问题** —— 一次一个，弄清目的／约束／成功标准
3. **提出 2-3 个方案** —— 各带取舍，并给出你的推荐
4. **分段呈现设计** —— 每段按其复杂度伸缩，每段后拿认可
5. **写设计文档** —— 存到 `docs/specs/YYYY-MM-DD-<主题>-design.md` 并提交
6. **规格自检** —— 快速过一遍占位符、自相矛盾、含糊之处、范围（见下）
7. **用户评审书面规格** —— 请用户看规格文件之后再继续
8. **转实现** —— 用 `writing-plans` 技能产出实现计划

## 规格自检（写完规格，对着它过一遍）

- [ ] **没有占位符**（没有 `<待定>`、没有 `TODO`、没有"等等"）
- [ ] **没有自相矛盾**（两处要求互相打架）
- [ ] **没有含糊**（"处理错误情况"这种——写清是哪些情况、怎么处理）
- [ ] **范围清楚**（写明**不**做什么）
- [ ] 每个决策都有理由

## 设计之后（架构路径）

设计被认可后：**转 `writing-plans`** 产出逐任务计划，然后按 `executing-plans`
或 `subagent-driven-development` 执行。

⚠️ **不要在设计被认可前就开始写代码。** 见过太多"设计还没定就先把代码写了"，
结果代码要按后来的设计重写一遍。

---

**与本项目的关系**：

- 本项目有 **plan mode（只规划）**：用户在界面选「只规划」时，这条路径就是那轮的全部产出
- 有界的改动可以用**隔离副本**（TS-061）做，失败直接丢弃
- 探索上下文用 `run_command` / `terminal` 跑 `cat` / `ls` / `grep` 等只读命令，**只读探索在硬门未完成时是允许的**
- 本项目还有 `doc-coauthoring`（写文档）与 `writing-plans`（写计划），
  它们分别是"规格写出来"与"计划写出来"的后续环节
