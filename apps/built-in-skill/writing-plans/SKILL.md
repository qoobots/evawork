# 写实现计划

## 概述

为**没看过这个代码库、也没看过这份规格**的工程师写实现计划。假设：一旦他知道确切的接口和确切的测试，他就能写出符合项目语言的惯用代码；计划留白的地方他会做出合理选择。

**他猜不到的是你决定过的事**：哪些文件、叫什么名字、签名长什么样、规格里哪些值要被用上、哪个测试证明哪个任务做完了。

**把这些写下来。** 然后把整份计划拆成一口能吃掉的任务。DRY。YAGNI。TDD。勤提交。

**开工时先说一句**："我在用 writing-plans 技能写实现计划。"

**存到**：`docs/plans/YYYY-MM-DD-<功能名>.md`
- （用户指定别的位置就听用户的）

## 范围检查

如果规格覆盖了**多个互相独立的子系统**，那它本应在头脑风暴阶段就被拆成多个子规格。
如果没有，建议现在拆成独立计划——**一个子系统一份**。每份计划都要能独立产出**可运行、可测试**的软件。

## 文件结构（先定这个，再拆任务）

- 边界清楚、接口明确的单元。每个文件**只有一件**明确的事。
- 你对"一次能装进上下文的代码"推理得最好，文件聚焦时改动也更可靠。**宁要小而聚焦，不要大而包办一切**。
- 总在一起改的文件应该住在一起。按**职责**拆，不是按技术分层拆。
- 已有代码库里，跟随既有模式。如果这个库就是大文件风格，别擅自重构；但如果你要改的那个文件已经臃肿到难办，把拆分写进计划是合理的。

这个结构决定任务怎么拆。**每个任务都应该产出独立说得通的改动。**

## 任务粒度

一个任务 = **最小的、自带一轮测试周期、值得被一个评审者把关**的单元。

拆任务时的判据：
- 配置、脚手架、文档步骤 → **折进**真正需要它们的那个任务里
- 只有当"评审者可以认可 A 同时否决 B"时，才拆开

**每个任务都以一个可独立测试的交付物结束。**

## 步骤粒度

**每一步是一个动作 + 一个可检查的结果**：

- 「写一个失败的测试」—— 一步
- 「跑它，确认它失败」—— 一步
- 「写刚好能让它通过的最少实现」—— 一步
- 「跑测试，确认通过」—— 一步
- 「提交」—— 一步

## 计划文档头（**每份计划都必须以此开头**）

```markdown
# [功能名] 实现计划

> **给执行的智能体：** 必需子技能：用 subagent-driven-development（推荐）或
> executing-plans 逐任务执行本计划。步骤用复选框（`- [ ]`）语法跟踪进度。

**目标：** [一句话说明这次要做出什么]

**架构：** [2-3 句说明做法]

**技术栈：** [关键技术／库]

**规格：** [本计划所实现的规格／设计文档路径——计划是从规格推导出来的，
所以规格要跟着计划一起走，执行者两个都要读]

## 全局约束

[规格里的项目级要求——版本下限、依赖限制、命名与文案规则、平台要求——
每条一行，数值照抄规格。每个任务的要求都隐含包含本节]

## 评审重点

[规格暗示了、但**没有任何任务的测试覆盖**、且最可能咬到真实用户的
五类输入或失效模式——每条一行，写清是哪个输入/条件，以及一个理性的人
会预期什么行为，最可能的排最前。]

**规格是愿景文档**：它说明软件必须做什么，不代表它会遇到的每一种情况；
**它对某个输入的沉默，不等于许可该输入让程序崩溃。** 拿着规格把这份清单
一次写完；然后为每一条补上钉住它的测试，放进拥有那段代码的那个任务里。
```

## 任务结构

````markdown
### 任务 N：[组件名]

**文件：**
- 新建：`确切/路径/file.ts`
- 修改：`确切/路径/已有文件.ts:123-145`
- 测试：`tests/确切/路径/test.ts`

**接口：**
- 消费：[这个任务用到的前序任务产出——确切签名]
- 产出：[后续任务依赖的东西——确切的函数名、参数与返回类型。
  任务的执行者只看得到自己那个任务；这一块就是让他知道邻居用什么名字和类型]

**步骤：**
- [ ] **步骤 1：写失败的测试**
  ```typescript
  test('...', () => { ... });
  ```
  → 跑 `npm test path/to/test.ts`，**确认它以正确的方式失败**

- [ ] **步骤 2：写最少实现**
  ```typescript
  export function verifyIndex(...) { ... }
  ```
  → 跑测试，确认通过

- [ ] **步骤 3：重构**
  （在保持全绿的前提下清理；每改一下重跑测试）

- [ ] **步骤 4：提交**
  提交信息：`feat(index): 新增 verifyIndex 覆盖 4 类问题`
````

## 自检（写完计划，对着规格过一遍）

- [ ] 每一步都能被**独立验证**（有明确的"怎么算做完了"）
- [ ] 每个文件路径都**确切存在或将被创建**（不是"可能改一下 utils"）
- [ ] 每个接口都写清了名字与类型（执行者只有这一份信息）
- [ ] **每个任务都能独立测试**（不依赖后面任务才能验证）
- [ ] 全局约束里的数值是**照抄**规格的，不是凭记忆写的
- [ ] 「评审重点」里的每一条都有对应的测试
- [ ] 没有"等等"、"类似上面"、"你知道的那些"这种含糊表述

## 交付执行

计划写完后的选择（问用户，别自己决定）：

1. **在当前会话里逐任务执行** —— 用 `executing-plans` 技能
2. **派子代理逐任务执行** —— 用 `subagent-driven-development` 技能（每个任务一个全新子代理，
   配任务评审，质量更高）
3. **先不做** —— 存档计划，之后再执行

告诉用户计划存在哪、包含哪些任务、需要他们做什么决定。

---

**与本项目的关系**：

- 用 `run_command` / `terminal` 把计划写到文件（尊重已有文档：改已有文件用 `sed`/`python` 等做局部替换，不要整文件覆写）
- 执行期用 `run_command` / `terminal` 维护一份 markdown 任务清单，让进度可见
- 本项目有 **plan mode（只规划）**：用户在界面上选「只规划」时，写计划就是那轮的全部产出，
  **不要动手改文件**
- 大改动建议先开**隔离副本**（TS-061），失败直接丢弃
