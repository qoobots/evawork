# 执行实现计划

## 何时用

**用**：搭档明确选择"在当前会话里逐任务执行"；或任务之间有顺序依赖、并行会打架；
或任务很小（1-3 个）不值得派子代理。

**不用**：任务相互独立且不少（≥4 个）→ 用 `subagent-driven-development`（质量更高）。

**前提**：计划已经存在（`writing-plans` 的产出），且**搭档已经认可**。
没有计划就开��，等于跳过了头脑风暴与计划评审——**不要这样**。

## 流程

```
读计划 → 准备环境 → ┌─ 任务循环 ─┐ → 最终评审 → 收尾
                      │ 1. 取任务   │
                      │ 2. 做步骤   │
                      │ 3. 完成契约 │
                      │ 4. 收尾任务 │
                      └─────────────┘
```

## 准备

执行前一次性做完：

1. **通读计划** —— 有疑问**现在就问**，别做到一半才回头
2. **确认计划文件路径**与目标分支/工作区
3. **验证基线** —— 跑一次现有测试，确认**动手之前它是绿的**
   ⚠️ 基线就是红的（本来就失败），你后面永远分不清是谁弄坏的
4. 建 todo 列表，一个任务一条
5. 声明："我开始用 executing-plans 执行这份计划"

## 任务循环

### 1. 取任务

从计划里挑下一个未完成的任务（按顺序）。读它的：**文件 / 接口 / 步骤**。

一次只做一个任务。**同时开三个任务 = 三个半成品**。

### 2. 做步骤

按计划里的步骤逐条执行，每个步骤：

- 做完**立刻**按步骤里写的验证方式确认
- 用 `sed`/`python`/`patch` 等改已有文件（不要整文件覆写）
- 改完**重跑测试**
- 大改动或不确定时，先开**隔离副本**（TS-061）——改砸了直接丢弃

⚠️ 步骤里写了"确认它以正确的方式失败"，就必须真的看它失败。
跳掉这一步就等于没在 TDD。

### 3. 完成契约（Completion Contract）

**每个任务结束时，逐条检查：**

- [ ] 计划里的**每个步骤**都做了？（对照清单，不凭记忆）
- [ ] 测试**都通过**？（跑一次，看完整输出）
- [ ] 新增/修改的文件**都处理了**？（计划里有具体路径，一个都不能漏）
- [ ] 计划里提到的**接口签名**与实际一致？（后面任务依赖它）
- [ ] 没有顺手做了计划之外的事？
- [ ] **提交**（计划里写了提交信息就用它）

⚠️ 任何一条不满足，**先补完再进下一个任务**。
"大概都做了"是任务之间互相污染的最常见原因。

### 4. 收尾任务

在 todo 上标记完成，**把结果告诉搭档**（一行即可：做了什么、测试过没）。
然后进下一个任务。

## 最终评审

**所有任务做完后**，回到起点整体看一遍：

1. **重跑完整测试套** —— 读完整输出
2. **对照原始需求/规格逐条核** —— 不是对照计划，是对照**最初的意图**
3. **看 diff** —— `git diff`/`git log`：有没有顺手改的、漏改的
4. **过一遍"评审重点"** —— 计划头部那一节列的输入类别，有测试覆盖吗
5. **确认没有"遗留待办"被当成"已完成"** —— 计划里明写"暂不做"的项，不能悄悄算进去

⚠️ 逐条核对需求时**发现缺口**，就如实报告缺口，不要说"基本完成"。

## 收尾

1. **提交**最后一个任务
2. **按 `finishing-a-development-branch` 处理分支**（合并／开 PR／保留）
3. **报告**：做了什么、验证结果、**没做什么**、建议的下一步

## 常见借口

| 借口 | 事实 |
|---|---|
| "计划里有几处我觉得不对，先按我的来" | 说出来，问过搭档再改。**默默按自己理解做 = 计划白写** |
| "这个任务太小了不用走流程" | 小的任务也要走完成契约——完成契约几乎不花时间 |
| "顺手把这个 bug 也修了" | 计划外的改动混进来，评审时会说不清。要做就另开一个任务 |
| "测试等全部做完再跑" | 中间不跑，最后一次失败的定位成本是十倍 |
| "跳过基线验证，测试本来就是好的" | 你怎么知道？跑一次 |
| "做完了，直接说完成" | 先过最终评审 |

## 流程示例

```
[读计划] 3 个任务：验证函数 → 接线 → 文档

准备：跑现有测试 → 34 通过（基线绿）

任务 1：写 verifyIndex()
  步骤 1：写失败测试 → 跑 → 以正确方式失败 ✓
  步骤 2：写最少实现 → 跑 → 通过 ✓
  步骤 3：重构 → 跑 → 通过 ✓
  步骤 4：提交 ✓
  完成契约：4 条全对 ✓ → 报告 → 下一任务

任务 2：接线 ...（同上）

最终评审：全套件 38 通过；对照需求 3 条全对；diff 无计划外改动
收尾：按 finishing-a-development-branch 处理 → 报告
```

---

**与本项目的关系**：

- 全程用 `run_command` 跑真实命令，**读完整输出**（别只看最后一行）
- 用 `run_command` / `terminal` 维护一份 markdown 任务清单，让进度可见
- 用户在界面勾了**「在副本里改」**（TS-061）时，整个循环跑在副本里，
  失败直接丢弃、不影响工作区；合回前会留回滚点
- 需要"派子代理做"时切换到 `subagent-driven-development`
- 相关：`writing-plans`（写计划）、`test-driven-development`（每步都适用）
