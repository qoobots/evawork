# 系统化调试

## 概述

**核心原则：找到根因再修。**

"改一下看看好了没"不是调试，是碰运气——
而且它会把 bug 留在原地，只是让它更难被发现。

## 铁律

```
没有找到根因，就不要改任何代码
```

症状和病因是两回事。空指针是症状；真正的病因是某处**该判空却没判**。
只治症状，几天后同一个 bug 会换个地方回来。

违反它的字面，就是违反它的精神。

## 何时使用

**任何**异常行为出现时——测试失败、报错、结果不对、性能骤降。
**尤其是**：
- 修过一次、没修好
- 修过好几次、反复出现
- 影响面不明
- 你还不确定问题在哪

## 四个阶段

**不要跳阶段。** 每个阶段都有明确的产出，跳过就是回到碰运气。

### 阶段 1：根因调查

**目标：搞清楚错误从哪来、怎么传播到这里的。**

1. **稳定复现** —— 找不到稳定复现就谈不上调试。记下：输入、命令、环境、结果
2. **读完整错误** —— 堆栈最底层那行才是真凶，上面的是调用链
3. **追踪数据流** —— 从报错处往上追：变量哪来的、值怎么变的、在哪变错的
4. **查最近变更** —— `git log`/`git diff` 看最近改了什么。**很多 bug 是上一次改动带来的**
5. **列出候选假设** —— 写下来，一个字一行。别在心里想

⚠️ **边界是首要怀疑对象**：空值、空数组、0、空字符串、越界、并发、编码、大小写。
经验上大部分 bug 都在边界上。

### 阶段 2：模式分析

**这一步决定"这次修好"还是"下次再犯"。**

1. **这个错误以前发生过吗？** 同类模式之前修过吗？当时的修法是什么？
2. **同类错误在别处还有吗？** 如果这里漏判空，隔壁那段大概率也漏了
3. **为什么**现在才暴露？之前"能跑"只是没触发
4. **是回归还是新 bug？** 查上次这个功能正常是什么时候

如果发现是**重复模式**（第 3 点成立），那就不是修一个 bug，是要加一道防线。

### 阶段 3：假设与检验

**一次只验一个假设。**

1. 写出假设：「我认为是 X 导致的」——写成能**被证伪**的句子
2. 找到**最省事**的验证方式（加一行日志、跑一个用例、改一个条件）
3. 验：
   - 假设成立 → 进阶段 4
   - 不成立 → **换一个**假设，回到阶段 1
4. **不要一次改多处**——改多处后你不知道是哪一处起了作用

⚠️ 改代码"试一下"不是验证假设——那只是换一种碰运气。
验证必须是**针对性**的：能明确区分"假设成立"与"假设不成立"。

### 阶段 4：实现

1. **最小修复** —— 只改根因那一处，不顺手重构、不顺手优化
2. **加回归测试** —— 用例必须能在**修复前失败、修复后通过**
3. **跑完整测试套** —— 确认没打破别的
4. **验证再验证** —— 回到阶段 1 的复现步骤，确认真的好了

**多重根因**：如果确实是多个独立成因，一个一个修，每个修完都跑测试。

## 红旗 —— 看到就停

| 想法 | 事实 |
|---|---|
| "改一下看看能不能好" | 碰运气。回到阶段 1 |
| "我扫一遍所有可疑点都改了" | 你已经毁掉了定位能力。而且大概率引入了新问题 |
| "加个 try/catch 就好了" | 那是藏错误，不是修错误 |
| "这是偶发问题" | 偶发**也是**问题，且更能暴露根因。**偶发 ≠ 不存在** |
| "先改着，等下再补测试" | 不会补的。回归测试是这次修复的一部分 |
| "报错信息看着像那个库的 bug" | 先确认版本与最小复现，别急着甩锅 |
| "修好了，跑一下就行" | 跑**完整**套件 + 回到原始复现步骤 |

## 搭档给你的信号

出现下面这些，说明你正在做错：

- "你确定看的是那行代码吗？" → 你在猜，没读
- "我早就说过那里有问题" → 你跳过了边界检查
- "每次都是这个错" → 你上次没找到根因
- "这个 bug 我修过" → 你修的是症状

## 常见借口

| 借口 | 事实 |
|---|---|
| "改了三处其中一处肯定有用" | 你不知道是哪一处。**一个假设一次验证** |
| "日志打了，问题就在那儿" | 日志证明现象，不证明根因 |
| "这是偶发的，不值得深究" | 偶发的根因通常更深 |
| "先发版，根因以后查" | 根因会一直影响下一个版本 |

## 速查

```
1. 复现不了 → 收集信息，别动手
2. 读完整错误 → 堆栈最底层
3. 追数据流 → 值从哪来、哪变错
4. 查最近变更 → 是不是回归
5. 列候选假设 → 写下来
6. 一次验一个 → 能证伪的那种
7. 找模式 → 以前发生过吗、别处还有吗
8. 最小修复 → 只改根因
9. 回归测试 → 修前失败、修后通过
10. 跑全套件 + 回原复现步骤
```

## 当查下来"没有根因"

有些 bug 真的找不到单一根因（并发时序、外部依赖、平台差异）。这时候：

1. **如实说**："没能定位到根因"
2. 记录**已排除**的假设（省下下次的时间）
3. 加**观测**：临时日志 / 断言 / 复现夹具，让它下次能被抓住
4. 给出**缓解**方案并说明它不解决根因

**"我修好了"必须能指出**是哪个假设成立、**证据**是什么。
