# 文档协作

## 为什么先问再写

技术文档失败的原因几乎从不是文笔，是**没问清给谁看、要解决什么**。
所以这个技能的第一件事永远是澄清，而不是起草。

开工前必须明确（一次问完，别挤牙膏）：

1. **读者是谁**：同组工程师／跨部门／客户／未来的自己
2. **要他们做什么**：读完能做出的决定或动作
3. **范围边界**：这次**不**覆盖什么（最容易被跳过，也最值钱）
4. **有没有现成材料**：现有代码、接口、历史文档——不要凭空重写已有内容

## 起草

- **标题就说结论**。读者只看标题也能判断这篇讲什么。
- 先写「问题」，再写「方案」。反过来读者会不知道自己为什么要读。
- 例子比形容词有用：一个具体的输入输出，胜过十句「更加友好」。
- 有取舍就写取舍。**不写取舍的方案读者不会信**。

## 落盘

- 改已有文件用 `sed`/`python`/`patch` 等做局部替换（精确替换），**不要整文件覆写**——覆写会丢掉别人刚改的内容。
- 新建文档前先用 `run_command` / `terminal` 跑 `ls` / `find` / `grep` 看有没有同类文档，**沿用现有结构与命名**，别另起一套。
- 写完把改动路径列给用户，并说明每一处改了什么。

## 收尾自检

- 有没有一句是读者不需要的？
- 有没有「显然」「众所周知」这类把读者当内行的词？
- 每个结论能不能追到材料（代码／数据／决策记录）？

工具以运行时注入的「可用工具」清单为准（系统提示会列出当前全部工具，含 MCP）。文件读写、列目录、搜内容、找文件、打补丁、删文件等优先用当前会话已接入的 MCP 工具；MCP 没有覆盖的再用 `run_command` / `terminal` 发 shell 命令兜底；加载技能用 `load_skill`，派子代理用 `delegate`。
