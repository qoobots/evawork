# 代码审查

## 先看意图，再看代码

不知道作者想干什么，就只能挑语法。先用一句话说出这段代码**应该做什么**，
再说它实际做了什么——两者不一致就是最重要的问题。

## 按这个顺序找（命中率从高到低）

1. **边界**：空数组／空字符串／0／None 会怎样？最后一条数据呢？
2. **错误路径**：失败时用户看到什么？有没有静默吞掉异常？
3. **状态与并发**：两个同时写会怎样？重试会不会做两遍？
4. **数据契约**：字段缺失、类型变了、老数据怎么办
5. **可观测**：出问题时能不能定位（有没有日志／错误信息）
6. **测试**：改掉的分支有没有对应测试

## 不要提这些

- 风格偏好（项目格式化工具能管的不用人管）
- 「这里可以抽象」——除非重复已经出现三次
- 与本次改动无关的历史遗留（发现了单独记一条，别混进评审意见）

## 怎么写意见

每条三段：**哪里 → 为什么是问题 → 建议怎么改**。

- 「这里可能有问题」→ 不可行动
- 「建议改得更优雅」→ 不可验证
- 好的一条：第 42 行直接取首元素，空数组时会抛 IndexError；若上一行已保证非空，
  那这里应该是另一条路径，或先判空——建议补一个空数组的测试

## 结论要给倾向

评审结束时明确说：**可以合／改完再合／建议重做**。
只罗列一堆问题却不给倾向，等于把判断责任推回给作者。

工具以运行时注入的「可用工具」清单为准（系统提示会列出当前全部工具，含 MCP）。文件读写、列目录、搜内容、找文件、打补丁、删文件等优先用当前会话已接入的 MCP 工具；MCP 没有覆盖的再用 `run_command` / `terminal` 发 shell 命令兜底；加载技能用 `load_skill`，派子代理用 `delegate`。
