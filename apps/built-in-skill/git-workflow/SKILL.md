# Git 操作

## 先看状态，再动手

任何 git 操作前先跑 git status 看清楚：有没有别人的未提交改动、有没有未跟踪文件。
**不要覆盖或丢弃不属于你的改动**——那比操作失败严重得多。

## 提交信息

写给三个月后的自己和同事看，不是写给工具解析的。

- 第一行：动词开头 + 一句话说清做了什么（不超过 50 字）
- 空一行后写正文：**为什么**做这个（不是做了什么，diff 自己会说）
- 有破坏性变更、迁移步骤、性能影响，单独标注
- 不要在信息里写「修复 bug」「更新代码」这种零信息量的话

例：修「登录后白屏」→
`修复：登录后白屏 —— 刷新页面时 token 已被清理，接口 401 后没跳登录页直接渲染空壳；补充重定向并加测试`

## 分支

- 一个分支做一件事。混了两件事的分支既不好 review 也不好回滚
- 命名带上类型前缀（feat/fix/refactor/docs），一眼能看出意图
- 发出去前整理历史（squash 成逻辑单元），别把「改了三行、改了一行、调格式」拆成三个提交给人家看

## 破坏性操作

**reset --hard / clean -fd / checkout -- 这类命令会丢东西，执行前必须确认**：

1. 先 git status 确认没有未提交的改动
2. 有未提交改动就先 stash 或提交，不要硬来
3. 明确说出这条命令会做什么，再执行

## 与回滚点配合

在 EvaWork 里做高风险重构时，可以先建隔离副本或留回滚点再动手——
git 能管提交，管不了「我还没提交就被覆盖掉」的场景。

工具以运行时注入的「可用工具」清单为准（系统提示会列出当前全部工具，含 MCP）。文件读写、列目录、搜内容、找文件、打补丁、删文件等优先用当前会话已接入的 MCP 工具；MCP 没有覆盖的再用 `run_command` / `terminal` 发 shell 命令兜底；加载技能用 `load_skill`，派子代理用 `delegate`。
