# 更新说明

## 先把事实取回来，不要凭印象写

版本说明最容易写成「感觉这版做了挺多事」。按顺序取材：

1. run_command 跑 git log（上一个 tag 到 HEAD），没有 tag 就用最近一次发布点
2. 用 git diff --stat 看改动规模与集中在哪些目录
3. 关键改动去读 diff 摘要，不要只看 commit 标题

**没有 git 仓库就如实说**（「拿不到提交历史，以下基于当前代码与我的记忆，可能不全」），
不要编造看起来很像那么回事的条目。

## 写给谁看

用户关心的是**自己的东西会不会坏**：

- 修了什么 bug（说清原来的现象）
- 加了什么能力（怎么用起来的，举个具体例子）
- 有什么**破坏性变更**（要改配置／改用法／数据会丢）——这段不能省

## 格式

    ## x.y.z（日期）
    ### 新增
    - 能力：一句说清怎么用（用户视角，不是实现视角）
    ### 修复
    - 现象 → 原因（用户不需要知道类名）
    ### 破坏性变更
    - 改了什么 + 用户要做什么 + 不改会怎样
    ### 内部
    - 重构、依赖升级（可折叠，用户不必逐条读）

## 纪律

- **不夸大**：没做的不写；「大幅提升」要能给出具体数字，否则删掉
- 内部改动（重命名、格式化）与用户无关，归入「内部」或干脆不写
- 一条一件事；把三件事塞进一条，用户会全部忽略

工具名以当前可用清单为准（read_file / list_dir / grep / write_file / patch / run_command / todo_write / delegate / load_skill）。
