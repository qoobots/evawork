# 子代理驱动开发

## 何时用

**用**：执行一份已有计划；任务**相互独立**；任务数 ≥ 3；每个任务都能独立测试。

**不用**：任务 < 3 个，或任务之间有顺序依赖 → 用 `executing-plans`。

**前提**：计划已存在且被认可；子代理工具可用（本项目是 `delegate`）。

## 核心机制

```
计划
 │
 ├─ 任务 1 → 实现子代理（全新上下文）→ 任务评审 → 修复循环 → 完成
 ├─ 任务 2 → 实现子代理（全新上下文）→ 任务评审 → 修复循环 → 完成
 └─ 任务 3 → ...
                                                ↓
                                          最终评审（全任务）
```

**为什么每个任务换一个全新子代理？**
- 干净上下文 = 只看这个任务，不被前面的讨论带偏
- 实现者的思维不会污染评审者
- 评审者的怀疑不会让实现者为了自保而将就

## 模型选择

派子代理时**显式指定模型**，不要用默认值：

- **实现类任务** → 用**强模型**（代码质量是重点）
- **评审类任务** → 用**强模型**（评审需要判断力）
- **机械类任务**（改配置、写文档、搬文件）→ 用**快模型**省钱

⚠️ 省钱的正确做法是"简单任务用便宜模型"，**不是"全部用便宜模型"**——
评审用弱模型等于没评审。

## 任务循环

### 1. 派实现子代理

`delegate` 出去，goal 里写清（**不要**把你的会话历史给它）：

- **任务是什么**（来自计划的哪个任务）
- **文件**：新建/修改的确切路径
- **接口**：消费什么、产出什么（确切签名）
- **必须遵守**：TDD（先写测试、看着它失败）、改文件用 patch
- **验证方式**：跑什么命令、期望什么输出
- **边界**：子代理内部是 **never 档**，写文件/命令会被拒——所以**让它只出方案与补丁，由你（主任务）执行改动**，
  或者给它明确的可执行动作并接受它会被拒

> ⚠️ **本项目的特殊约束**：`delegate` 的子代理是 **fail-closed**（不会弹审批、
> 写文件/跑命令一律拒绝）。所以"派它直接改代码"这条路在 EvaWork 上**走不通**。
>
> **可行做法**：子代理负责**实现方案 + 补丁内容**（纯文本产出），主任务负责落盘与跑测试。
> 这既是本项目的约束，也恰好是一种**更安全的分工**：改动的最终执行权在主任务手里。

### 2. 处理报告

子代理返回后，检查它**实际做了什么**（不是它说做了什么）：

- 补丁/方案是否覆盖了任务的全部步骤
- 有没有计划外的改动
- 有没有说"我改不了"的地方（需要你接手）

### 3. 任务评审

**派一个独立的评审子代理**（全新上下文），给它：

- `{DESCRIPTION}` 这次做了什么
- `{PLAN_OR_REQUIREMENTS}` 这个任务应该做到什么
- 实际改动（diff 或补丁内容）

参照同目录的 [task-reviewer-prompt.md](task-reviewer-prompt.md) 与
[implementer-prompt.md](implementer-prompt.md) 组织提示词。

评审者只看**作品**，不看实现者的思考过程。

### 4. 修复循环

评审发现问题 → **派新的实现子代理**去修（不要自己顺手改——
自己改了就没人评审了）→ 再评审。

循环直到评审说"可以过"。**上限**：同一任务反复 3 轮还不过 →
**停下来告诉人**（可能是任务本身定义得不对，或者方案有问题）。

### 5. 完成

- 主任务落盘所有改动、**跑测试确认真 green**
- 更新 todo
- 报告一行

## 最终评审

全部任务完成后：

1. 重跑完整测试套（读完整输出）
2. 对照**最初需求**逐条核（不是对照计划）
3. 看整体 diff
4. 过一遍"评审重点"清单
5. 如实报告**没做的部分**

## 常见借口

| 借口 | 事实 |
|---|---|
| "我自己顺手改比再派一次快" | 没人评审你的改动。而且你不该同时扮演实现者与评审者 |
| "子代理说完成了" | **独立验证**（见 `verification-before-completion`） |
| "这个任务太小不用评审" | 小任务的错同样会阻塞后面所有任务 |
| "让它自己改就行" | 本项目子代理是 never 档，改不了；要它给补丁、你落盘 |
| "评审者理解不了上下文" | 那说明你没给够。给精确产物，别给思考过程 |
| "先往下做，评审最后一起" | 那就不是每任务评审了，等于没有 |

## 流程示例

```
准备：读计划 → 基线测试绿 → 建 todo

任务 1：新增 verifyIndex()
  派实现子代理 → 给出 TDD 补丁（先失败测试 + 最少实现）
  主任务落盘 → 跑测试 → 绿 ✓
  派评审子代理 → 返回：结构干净 ✓；Important：没处理空数组
  派修复子代理 → 补丁 → 落盘 → 测试绿 ✓
  再评审 → 可以过 ✓
  任务 1 完成

任务 2、3 同上

最终评审：全套件 38 通过；需求 3 条全对；diff 干净
```
