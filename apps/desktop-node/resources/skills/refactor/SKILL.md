# 重构

## 第一条铁律：行为不变

重构的定义就是**外部行为完全不变**。任何顺手改的行为（哪怕是「顺手修的 bug」）都要单独提交或单独说明，
混在一起会让 review 的人无法判断哪些变化是安全的。

## 顺序

1. **先让它是绿的**：跑测试，确认当前状态可复现。没有测试就先补最小覆盖
2. **一次只做一种改动**：提取函数 → 改命名 → 去重复 → 调结构。每步之间都是绿的
3. **小步提交**：每一步都能单独回滚。步子大了出问题很难定位
4. 重复以上

中途出现红灯（测试失败）就**停下**，不要"先全部改完再一起调"——那样无法判断是哪一处引入的。

## 优先动什么

按「收益 ÷ 风险」排序，先做高收益低风险的：

1. **删除**（死代码、无用的中间变量、注释掉的代码）——收益最高，风险最低
2. **改名**（名副其实的变量/函数名）——不改逻辑，最容易验证
3. **提取函数**（重复三次以上的逻辑、超过一屏的函数）
4. **调整参数与依赖**（最后做，最容易引入问题）

## 手法

- 改已有文件用 **patch**，不要整文件覆写（会冲掉别人的改动，且 diff 无法 review）
- 大重构前先记下当前测试结果，重构后跑一遍对比
- 不要在重构时顺手改命名规范、改 import 顺序、改格式化——那些交给格式化工具

## 收尾

重构完说明三件事：**动了什么结构、行为如何保证不变、还有哪些没动**（没动的也要说，避免下次误以为已经清干净）。

工具名以当前可用清单为准（read_file / list_dir / grep / write_file / patch / run_command / todo_write / delegate / load_skill）。
