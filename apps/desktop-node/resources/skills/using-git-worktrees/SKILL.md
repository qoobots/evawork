# 用隔离工作区开发

## 概述

在**当前目录**上直接大改，然后靠回滚点救场——这是被动的。
隔离是主动的：**在另一份副本上改，原工作区全程干净**。

**核心原则：动手之前先有一份可以随便砸的副本。**

## 步骤 0：先检查有没有已经在隔离里

开始之前先确认：当前是不是已经在一份隔离工作区/分支里？

- 是 → 告诉用户你已经在隔离里（避免他以为改动落在主工作区）
- 不是 → 进步骤 1

## 步骤 1：建隔离工作区

本项目（EvaWork）有**两条路**，按可用性选：

### 1a. 内置隔离副本（**默认，不依赖 git**）

界面上勾「**在副本里改**」，或让主任务调 `isolate/begin`。

- 复制工作区源码到 `.evawork/isolates/<名字>/`（依赖目录、构建产物、`.git` 都不复制）
- **不需要本机装 git、不需要工作区是仓库** ← 这是它比 git worktree 强的地方
- 改完看差异（`isolate/diff`），合回（`isolate/apply`，会先留回滚点）或丢弃（`isolate/abandon`）

⚠️ 建副本失败时**整轮不开始**并说清原因——绝不能悄悄照原工作区跑，
那等于把用户的工作区暴露在他以为受保护的场景里。

### 1b. git worktree（可选，本机有 git 且工作区是仓库时更标准）

```bash
git worktree add .worktrees/<分支名> -b <分支名>
```

⚠️ 注意：原生 `git worktree`（2.5+）与 `git worktree add` 参数不同；
第三方工具（含内部用的 `isomorphic-git`）**没有 worktree 子命令**——
所以这条路要看环境是否具备，不能默认成立。

## 步骤 2：项目准备

副本里可能缺少依赖/构建产物（我们刻意不复制那些）。按需：

- 安装依赖
- 生成代码
- 复制必要的本地配置（**别复制 .env 这类含凭据的文件**）

⚠️ **判断标准：装完之后基线测试是绿的吗？**
不是绿 → 隔离环境本身有问题，先修环境，别开始写代码。

## 步骤 3：验证干净基线

**这一步不能省。**

```bash
# 在副本里
<跑测试命令>
```

确认：**改动之前，测试就是通过的。**

理由：基线不绿的话，你永远分不清最后的失败是谁造成的。
"反正之前就有一个失败的"不是理由——**记下来**，完成后确认没变多。

## 报告

告诉用户：

- 副本在哪（路径）
- 基线状态（测试通过 / 本来就有 N 个失败）
- 打算在这里做什么

⚠️ **必须说清"改动还没进主工作区"**——否则用户会以为已经改完了。

## 速查

```
0. 已经在隔离里了吗？→ 告诉用户
1a. 内置副本（默认）：界面勾「在副本里改」/ isolate/begin
1b. git worktree（本机有 git 且是仓库时）
2. 装依赖 / 生成代码（凭据文件别复制）
3. 跑测试 → 必须绿（不绿就记下来）
4. 报告：副本路径 + 基线状态 + 改动还没进主工作区
5. 完成后：看差异 → 合回（留回滚点）或丢弃
```

## 常见借口

| 借口 | 事实 |
|---|---|
| "改动很小，直接在主工作区改" | "很小"是判断，不是事实。**回滚点能救文件内容，救不了你误删的目录** |
| "先在主工作区试，不行再隔离" | 试完再隔离 = 已经改过了。顺序反了 |
| "复制一份太慢" | 省下的几分钟对比弄脏主工作区的代价，不成比例 |
| "我记着在副本里呢" | 靠记性不如靠明确路径 + 界面开关 |
| "基线本来就有失败的，忽略" | 记录下来，完成后确认**没变多** |
| "合回之后再撤销很麻烦" | `isolate/apply` **会先留回滚点**，合回这一步本身能撤 |

---

**与本项目的关系**：

- 界面：输入区的「**在副本里改**」开关（默认关）+ 副本卡片上的
  **查看差异 / 合回工作区 / 丢弃**三个按钮
- 主进程与 SDK：`isolate/begin` / `isolate/diff` / `isolate/apply` / `isolate/abandon`
- 副本落在 `.evawork/isolates/`，**在工作区内**（放工作区之外沙箱进不去）
- 合回前会自动留回滚点，于是"合"这个动作本身也能撤销
- 相关：`finishing-a-development-branch`（收尾）、`executing-plans`（在副本里执行计划）
