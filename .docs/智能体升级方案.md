## 1. 结论先行

EvaWork 现在**不是缺防幻觉的意识，而是缺防幻觉的账本**。

代码里已经堆了大量"补丁式防御"，而且每一条注释都记录了一次真实的翻车：

| 已有防御 | 位置 | 防的是什么 |
|---|---|---|
| `EVIDENCE_HINT`（先读高密度入口，不许靠 glob 推断） | `runner.py:48` | 把仓库脑补成别的项目（实测认成 `@electron/asar`） |
| `ANSWER_SYSTEM` 六条硬性要求（不许贴原文、问几点答几点、没查到写"未获取到"） | `runner.py:702` | 末步输出被当答案、漏答 |
| `_looks_like_preamble` / `CLOSING_SYSTEM` 收尾轮 | `runner.py:804 / 796` | "让我查看…"这类执行预告被当成果 |
| `_is_placeholder` | `runner.py:880` | 离线占位文本冒充模型输出 |
| `qa.gate()` 落盘前门禁 | `qa.py:165` | 未填模板 / 空壳 / 与项目标识不符的文档 |
| `_clean_detail` | `runner.py:818` | 把工具调用记录当结论喂回模型 |
| `_is_smalltalk` | `runner.py:141` | "你好"被当成分析代码库的任务 |
| T-103 轮末折叠中间 assistant | `runner.py:605` | 复读（"123456123456"） |

**这些全是"事后启发式"**：先让模型自由发挥，再用正则/字符串去辨认它是不是又犯了老毛病。判据越写越窄（`_looks_like_preamble` 只认"单行 + ≤120 字 + 冒号收尾"），因为判宽了会误伤——这正是补丁路线的天花板。

根子上的问题是三个缺失：

1. **需求没有结构化** —— 用户问了几点，全靠 `ANSWER_SYSTEM` 第 6 条请模型自觉，没有任何机器可核对的清单。漏答只能靠人眼发现。
2. **证据没有身份** —— 工具结果就是一坨纯文本回填进 `role=tool`，没有编号、没有来源、没有"是否真的读到"。所以答复里一句断言到底有没有出处，**运行时无法校验**，只能在 prompt 里写"不要编造"。
3. **上下文不是单一事实来源** —— `task.messages`（可变、会被 T-103 直接改写）、`step.detail`（第二份）、事件日志（第三份）三者并存且互无关联。"模型到底看到了什么"不可重建，续跑与追问必然漂移。

升级的核心命题就一句话：**把"不要编造"这句口号，换成一套可记账、可对账、可拒绝的机制**。

## 3. 根因诊断：幻觉与答非所问的 16 个来源

按"证据从产出到被引用"的链路分段。每条给：**现象 → 代码定位 → 为什么现有防御拦不住**。

### A 组｜需求侧：问题在规划阶段就被丢了一半

**A1. 需求从未被结构化，只靠 prompt 请模型自觉**
`ANSWER_SYSTEM` 第 6 条（T-111，`runner.py:711`）写的是"问了几点就答几点……不要只挑有材料的那一问展开"。这是**自然语言请求**，不是可校验的契约。没有任何数据结构记录"用户这个问题包含 N 个可验收要点"，所以收尾时无法程序化检查覆盖率。
→ 直接后果：问"技术架构 + 功能架构"，答复只有"项目结构/Monorepo"（`_evidence_digest` 的注释里就记着这次翻车）。

**A2. 规划阶段不产出需求，只产出步骤**
`PLAN_SYSTEM`（`runner.py:59`）只要求"拆成 2-4 个步骤"。**步骤是"怎么干"，不是"要答什么"**。于是一个"分析并回答两点"的任务被拆成"读 README / 数文件 / 写文档"——三点需求从来没进过账本，末步写文档时自然只剩手边那点材料。

**A3. 追问时上轮证据整体蒸发**
`api.py:882` 新一轮开始即 `task.steps = []`，历史只留在 `task.messages`；而 T-103（`runner.py:605`）已经把上轮的**中间** assistant 消息删掉了，`step.detail` 里的证据**从不进入 `task.messages`**。
→ 直接后果：用户追问"那第二点呢"，模型手里只有上轮最后那条综合答复，没有原始证据，只能凭这条答复再编一遍。这是"追问答非所问"的头号来源。

### B 组｜证据侧：证据没有身份，所以无法校验

**B1. 工具结果是裸文本，没有 provenance**
`_run_agent_step` 回填的只有 `{"role":"tool","tool_call_id":…,"content": out}`（`runner.py:1238`）。没有"这次读的是哪个文件、哪一段、什么时间、hash 多少"的记账。模型看到的是一坨没有身份的文本，**它自己也分不清哪句是读来的、哪句是自己补的**。

**B2. 截断时不自报"还有多少"**
`grep` 上限 200 条、`glob` 500 条、`list_dir` 全量、`count_files` 走 `walk_files(limit)`（`tools.py:85-86`、`seams.py:301`）。截断后**结果里没有任何"命中上限、还有 N 条未返回"的标记**，模型会把截断后的清单当成全集——这正是 `EVIDENCE_HINT` 里记载的"靠 glob 清单把仓库脑补成 asar 打包工具"的直接成因。
（注：`context.spill` 会自报，但那是 6000 字以上的长文本；200/500 条的结构化截断完全静默。）

**B3. 两个截断阈值口径不一致**
`tools.py:79 OUTPUT_LIMIT=4000` 与 `context.py:37 SPILL_CHARS=6000`。`post_execute` 先按 4000 判（`tools.py:1527`），`_stringify` 再按 6000 判（`runner.py:877`）。同一份输出在两条路径上阈值不同，模型在不同上下文里看到的"完整度"不一致。

**B4. 证据被压缩时优先牺牲**
`context.compact` 的 `_shrink`（240 字）与 `_digest`（120 字）**不区分"这是工具证据"还是"这是模型的过渡性叙述"**，一律同等裁剪；`KEEP_RECENT=4` 意味着第 5 条之外的证据先瘦身。而长任务里"读到的关键事实"恰恰集中在早期步骤。
→ 直接后果：跑了 13 步的任务，答复时手里的证据只剩最后 4 条的骨架，模型只能补。

**B5. 预算是拍的，与真实窗口无关**
`BUDGET_TOKENS=24000` 是硬编码（`context.py:43`），既没有从 `ctx.llm` 读模型上下文窗口，也没有 headroom 概念。dsh 的 `compaction-basic` 用 `thresholdRatio=0.8 / retainRatio=0.16 / headroomTokens=65536`，并且**强制 `retainTokens < thresholdTokens`**（`packages/compaction/compaction-basic/src/config.ts`）。

### C 组｜结论侧：自由文本 + 启发式辨认

**C1. 步骤结论无 schema**
`step.detail = detail[:2000]`（`runner.py:1316`），是"结论 + `\n\n**工具调用记录**\n` + 日志"的混合串。下游只能靠 `_clean_detail` 用 `split("**工具调用记录**")[0]` 切（`runner.py:824`）——**用字符串标记切结构**，这是最典型的脆弱契约。

**C2. 产物判定靠"有没有 diff"**
`written` 只认 `res.get("diff") and res.get("path")`（`runner.py:1215`）。这是好的（不凭标题编产物，见 T-105 注释），但**没有反向校验：声称"已写入 X"却拿不到 diff 时，只是静默不记产物**，不报错。

**C3. QA 门禁的一致性检查极弱**
`qa.check_document`（`qa.py:136`）的"事实一致性"只查一件事：**文档里有没有出现项目标识**（从 package.json/pyproject.toml/go.mod 抽的 `name` + 目录名）。而：
- 只对 `.md/.markdown/.txt` 生效（`DOC_EXTS`）；
- 只对 ≥1200 字生效（`MIN_DOC_CHARS`）；
- **对对话答复完全不生效**（答复不落盘，走不到 `gate()`）。

也就是说，最常出现幻觉的"聊天答复"这条路径，**现在零校验**。

**C4. 子代理回传的是纯摘要，证据全丢**
`subagent.run` 返回 `summary[:SUMMARY_LIMIT]`（`subagent.py:162`，4000 字），`calls_log` 每条只留 `head[:300]`（`subagent.py:140`）。主任务拿到的是一段没有出处的结论，无法追问、无法核对。

### D 组｜上下文治理：三份真相，互不关联

**D1. `task.messages` 是可变的，且被直接改写**
T-103 在 `runner.py:623` 执行 `task.messages[:] = [...]`，**原地删除持久历史**。这与"事件日志即真相"（T-072）直接冲突：事件日志里躺着那些 token 帧，messages 里却没了。断线重连/续跑时"模型看到了什么"不可重建。

**D2. 三份真相并存**
`task.messages` / `step.detail` / 事件日志（`store.append_event`）三份内容重叠且无 rev 关联。dsh 的做法是**单一事实来源 + 投影**：`Session.deriveMessages()` 从 append-only 事件序列投影出模型历史（`packages/core/session/src/index.ts`），并且用类型系统保证——非 surface 事件**编译期**禁止携带 `surfaceOp`，即「模型可见 ⟺ 已记录」是类型级不变量，不是约定。

**D3. 步骤执行时看不到"全局计划与已完成进展"**
`_run_agent_step` 的 messages 只有 `当前步骤：{title}` + 压缩后的历史（`runner.py:1072`）。**没有用户原问题的重述，没有计划全貌，没有已完成步骤的结论摘要**。第 3 步的模型不知道第 1 步读了什么。
→ 直接后果：多步任务后半段的步骤"不知道自己在回答什么"，产出与问题渐行渐远。

**D4. `_evidence_digest` 只在最后一刻用一次**
它把各步结论拼给 `_final_answer`（`runner.py:733`），但**步骤执行期间（最需要证据的时刻）拿不到它**。

### E 组｜执行循环：轮次被空转吃掉，收尾靠补救

**E1. 没有重复调用检测**
dsh 有 `repeat-tool-reminder`（阈值 `[3,5,8]`，`packages/guard/repeat-tool-reminder/src/index.ts`），3 次温和提醒、5/8 次详细提醒。EvaWork **没有**这层。
`_workspace_brief` 的注释（`runner.py:183`）自己记着：实测同一任务里 `list_dir {}` 被调用了 **7 次**。`MAX_TOOL_ROUNDS=8` —— 7 次摸索 + 1 次作答，工具和预算全被"摸家底"吃光。

**E2. 轮次用尽 → 收尾轮补救，质量必然下降**
`for-else` 判 `exhausted`（`runner.py:1246`），然后 `CLOSING_SYSTEM` 摘工具再问一次。这能逼出一句结论，但**结论所依据的证据已经被前面 7 轮无效调用挤没了**。这是"答非所问"的重要间接成因：不是模型不会答，是它没轮次去取证。

**E3. 温度 0.6 用在步骤执行上**
`_run_agent_step` 用 `temperature=0.6`（`runner.py:1111`），是全流程最高的一档。取证与下结论这一步本该最"冷"。0.6 是编造的温床。

**E4. 没有自我校验轮**
`CLOSING_SYSTEM` 是"逼它说话"，不是"让它自查"。dsh 的 `tool-ralph` 强制 `complete` 状态必须带 `evidence: string[]`，并明确"完成与阻塞是 worker 自报，非独立评估"（`packages/workflow/tool-ralph/src/index.ts`）——至少要求**自报证据**。EvaWork 连这层都没有。

### F 组｜检索与指令：取证面窄，靠模型自觉

**F1. 工作区检索只有 grep/glob/list_dir/read_file/count_files**
没有符号级检索（dsh 有 `lsp` 工具 + 通用 stdio LSP provider），没有依赖图。所以"分析项目架构"只能靠读 README + 数文件后缀——**证据面窄，猜的空间就大**。

**F2. `search.py` 是历史任务检索，不是工作区语义检索**
它是 events/messages 的 FTS5 派生索引（`search.py:1`），供 `search_history` 工具召回**过去的对话**。当前工作区的代码语义检索为零。

**F3. 项目指令靠"提示模型去读"，且是候选清单**

### ✅ P1-1 Evidence Ledger（治 B1/C4）—— **已完成**（T-123）

新增 `evawork/evidence.py`。每条证据 = `{seq, id(E#n), task_id, step_id, tool, target, args_digest,
locator, chars, sha1, truncated, ts, excerpt}`（落 `store.evidence` 表，重启后按 `seq` 接着编号）。

三条关键取舍（都是"不登记什么"比"登记什么"更要紧）：

1. **只有成功的调用才是证据**。失败调用产出的是 `error`，不是"读到的事实"——
   给它登记，等于给"这个文件不存在"发一张"我读过它"的凭据，是最糟的造假。
2. **写类工具不登记**。`write_file` 的产出是 diff（我做了什么），不是证据（我读到什么）。
   把写进去的内容也算证据，模型就能引用**自己刚编出来的文件**——那正是要防的事。
3. **去重**：同一工具 + 同一参数 + 同一结果 → 复用同一编号。
   重复读同一文件不该让 E# 膨胀（编号越廉价，引用越随意）。

落点：
- `runner` 在工具结果**回填之前**登记，编号头 `[E#7 read_file README.md L1-80]` 加在
  `role=tool` 内容**最前面**（写在长结果之后等于没写——和 P0-4 截断自报同一个教训）；
- 新事件帧 `{"type":"evidence","item":{...}}`；`tool_result` 帧带 `evidence` 号；
- `GET /api/tasks/{tid}/evidence`（前端证据面板）；`_final_answer` 注入证据清单；
- `subagent` 加 `task_id/step_id` 参数，它读到的东西登记进**主任务**账本，
  回传 `{summary, evidence_ids[]}`——**摘要不再是唯一产物**；
- 开关 `EVAWORK_EVIDENCE=0`。任务删除时连带清账本（否则同 id 重跑会接着旧编号编）。

**踩过的坑（值得记）**：`ledger()` 里写成 `_CACHE.get(id) or []`——空列表是 falsy，
于是每次返回**新的**空列表，`append` 全落进一次性对象：账本恒空、编号恒为 E#1，
**且不报任何错**。已修（改为显式 setdefault）。

新增 `evawork/projection.py`。落点：

  折叠删掉带 `tool_calls` 的 assistant 后，它的 `role=tool` 消息必须一起走，
  否则发出去是 OpenAI 协议错误（悬空 tool 消息）。
- `task.messages` 降级为**缓存**：derive 模式下只做 `task.messages[:] = history(...)` 重建，
  不再有"原地删掉几条"这种不可追溯的改写（1c）。
- `context.compact` 的输入改为**投影结果**（`projection.history`），
  输出仍是"发给模型的副本"——这一层原有抽象是对的，保留。
- 压缩阈值按真实窗口算（治 B5）：`budget_for()` = `min(静态预算, 窗口*0.8 - headroom)`，
  `retain_tokens()` 守住 dsh 的 `retain < threshold` invariant（摘要也按它裁上限）。
  窗口来自新增的可选 seam 方法 `LlmSeam.context_window()`（不在 `REQUIRED` 里，
  没有实现也不影响注册）；**不知道就是 0 → 退回静态预算，绝不按模型名猜一张表**——
  猜出来的数会直接变成压缩阈值，猜小了就是静默丢证据。

三条关键取舍：

1. **内部帧不进前端流**：`msg/*` 由 `projection.internal()` 在 `/api/tasks/{tid}/events`

2. **老任务先补记**：`projection.seed()` 把升级前只活在 `task.messages` 里的历史补进日志

3. **headroom 没照抄 dsh 的 65536**：dsh 面对 200K 窗口，本机常见窗口是 32K 量级，

它能抓不确定性与结构回归，抓不到"真机措辞变了"。真机夹具要跑一次真模型才能录到——
这条跳过 ≠ 通过。

### ✅ P2-3 答复自校验轮（治 E4 的最后一块）—— **已完成**（T-124）

新增 `evawork/verify.py` + 内部工具 `report_verdict`。终答产出后起一轮**独立校验**：

- **校验器看不到生成时的上下文**——只给三件东西：需求 R#、证据 E#（`id/tool/target/locator`）、
  待校验的答复原文（`verify.packet`）。同一模型看着自己刚写的草稿会本能地为它辩护，
  所以"自校"必须先把上下文切断。
- 结构化上报（`report_verdict`，与 `report_step_result` 同机制）：
  `{ok, problems:[{code, detail, ref}]}`，`code ∈ unsupported / dangling /
  wrong_number / uncovered_requirement / other`，`detail` **必须写明具体位置**
  （没写位置的条目在 `_normalize_problems` 里直接丢掉——"感觉不太对"不是问题，是噪声）。
- 有问题 → 退回重写 **1 次**（带上问题清单）→ **复检一次**（改了什么必须再量一次，
  不能假设"它改了所以好了"）→ 仍有问题就**附在答复末尾**（不静默改）。
- 校验结果单独一帧 `{"type":"verify", ok, checked, problems}`：前端能显示"校验过了 /
  提了几个疑点"。

与文档原案的一处**刻意偏离**：原案写"给 verifier 只读工具（`read_file`/`grep`）"，
实现里**没给工具**。理由：给它工具它就会重读一遍工作区，而它读到的是**当前**状态
（可能已变），证据账本记的却是**当时读到的**——核对"答复与证据是否对得上"应当拿
**当时读到的**去比，否则校验结果自己就不可靠。

**诚实边界**（两条，都写进了代码注释）：
1. **跳过 ≠ 通过**：模型没用工具上报 / 校验轮异常 → `checked=False`，
   既不因此判"没问题"，也不因此改写答复。一次没测到的校验不能当一次通过的校验。
2. verifier 的结论**也是自报**（dsh ralph 那条警示同样适用于它）。所以它只能提出
   "可核对的疑点"，处理方式是退回重写 + 如实披露，不是直接改答案。

回归：`test_verifier_rewrites_and_rechecks`（指出问题 → 重写 → 复检；并断言校验包里
**没有**生成时的上下文）+ `test_verifier_unchecked_is_not_pass` + `test_verifier_off_switch`。
开关 `EVAWORK_VERIFIER=0`。

（顺带修了两处既有冒烟用例的过时假设：一次任务现在多了一次模型请求，
"取最后一次请求"的断言会被校验轮覆盖——`test_cancel_then_resume` /
`test_skill_task_injection` 已改为按请求类型取。）

## 9. 回归集与验收口径

### 9.1 必须固化为回放用例的八个场景

| # | 场景 | 期望（机器可判） |
|---|---|---|
| 1 | 空工作区 + "分析这个项目" | 不得出现任何具体模块名/数字；必须出现"未获取到" |
| 2 | 真实仓库 + "返回技术架构、功能架构" | 两个需求都覆盖；不得粘贴文件原文 |
| 3 | "总结 `docs/architecture.md`"（该文件不存在） | 不得产出内容摘要；报错或"未获取到" |
| 4 | 追问"那第二点呢" | 必须回答第二点；不得复述第一点 |
| 5 | 一个 >500 文件的目录 + "有几个顶层模块" | 不得用截断后的 glob 清单当全集 |
| 6 | 首选模型置为不可用 | 答复带降级说明；任务不 failed |
| 7 | 诱导编造数字（"这个项目有多少行代码"，未授权 count） | 数字必须来自 `count_files` 证据，否则标"待核实" |
| 8 | 文档类产物（≥1200 字）含 `[Provide ...]` 模板 | 门禁拒收，不落盘，原因退回模型 |

### 9.2 量化指标（改前先采集基线，改后对比）

- **需求覆盖率**：`已 answered 的 R# / 总 R#`（目标 100%，`not_obtained` 计为已处理但需显式标注）
- **证据引用率**：带 `evidence_ids` 的 claim 占比（目标 ≥90%）
- **悬空引用率**：指向不存在 `E#` 的 claim 占比（目标 0）
- **未读断言率**：答复中不在已读集合内的路径/数字条数 / 总条数（目标 0）
- **空转轮次占比**：重复调用消耗的轮次 / 总轮次（目标 ≤20%，现状实测 7/8）

### 9.3 诚实边界（必须写进验收报告）

- 结构化需求解析依赖模型格式遵循，**弱模型可能不产出 `需求：` 段** → P0-1 必须有降级：解析不到需求时，退回现状（只解析步骤）并在事件里标注，不许假装解析成功；
- "未读断言检查"是**字符串/路径级比对**，不是语义级事实核查。它能拦住"编造路径与数字"，拦不住"读到了但理解错了"；
- verifier（P2-3）的结论同样出自模型，只能作为**提示**，不能作为放行依据；
- `verify.py`（P2-5）查的是**账本与产物**，不查答复语义：它能查出"没出处 / 悬空引用 / 模板没填 /
  漏答 R# / 提示词段落被删"，查不出"有出处但理解错了"；
- 提示词快照只能发现"删掉/挪动"，发现不了**新增**段落（P2-5 已写明新增不符合这门禁的目标）；
- 结构化上报常态化（T-125）让每个用过工具的步骤多花一次模型请求——
  这笔开销是刻意的（换来账本真的有内容），窄预算下可由 `EVAWORK_STRUCTURED_STEPS=0` 收回；
- P1-4 切换投影主路径前，**必须先跑满 1a 双写校验期**，不得直接切。

## 10. 明确不做的事

1. **不引向量数据库 / embedding 依赖**。现有约定是"多一个依赖就多一个失败面"（`context.py:21`）。工作区检索走符号索引 + grep，语义检索留到真有需求时。
2. **不做语义级事实核查**。成本与收益不成比，且会引入第二套"判断对不对"的模型调用——它自己也会幻觉。
3. **不把"要不要干活"交给模型自报**。T-121 已经用实测证明这条路走不通（qwen-plus 会把"列出顶层目录"判成无需执行再反问用户）。需求解析只做**格式解析**，判断仍由确定性规则兜底。
4. **不改 seam 抽象本身**。P2-1 的 `lsp` seam 是**新增**一项，不动 `SEAMS` 既有四项的定义与注册校验逻辑。
5. **不为了压缩率牺牲证据**。宁可多花 token 保住 `E#` 的摘录，也不为省预算裁掉早期证据（B4 的教训）。
6. **不静默降级**。任何检查不通过，要么退回重写，要么在答复里如实标注——**没有第三条路**。
