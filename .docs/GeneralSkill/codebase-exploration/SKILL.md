# 代码库探索纪律

## 用专用工具，不用 shell

| 要做的事 | 用 | 不用 |
|---|---|---|
| 看文件内容 | `read_file` | `cat` / `type` |
| 找文件（按名字） | `search_file`（glob） | `find` |
| 搜内容（按正则） | `search_content` | `grep` / `rg` 直接跑 |
| 看目录结构 | `list_dir` | `ls` / `dir` |

专用工具返回结构化结果（行号、相对路径、忽略规则），后续引用和编辑都靠它。
大文件用 offset / limit 续读，不要一次吞整个文件。

## 先读后改

- **读过的文件才有资格被编辑**。没读过就 patch / write 是事故的头号来源。
- 有针对性改动用**局部编辑**（patch），不要整文件重写；重写前必须先读全文件。
- 编辑完不要为了"确认"再重读一遍——工具返回的结果就是事实。

## 探索策略

1. **从问题出发定搜索词**：报错信息原文、函数名、配置项，而不是泛泛的关键词。
2. **先窄后宽**：先在可疑目录里搜；没命中再扩大到整个仓库。
3. **顺着引用走**：找到定义后看谁在调用它（找引用），改动的影响面就清楚了。
4. **大范围扫描交给子代理**：跨目录、跨命名约定的普查，委派给只读子代理，
   只要结论和证据路径，不要全文转储。委派了就别自己重复搜，等结果。

## 历史与现状

- 疑问先查**当前代码**，再用 `git log` / `git blame` 查"为什么"。
- 不要凭记忆断言"这个文件里是 XX"——记忆会过期，重新读。

## 改动最小化

- 保持文件既有风格：命名、缩进、注释密度与周围代码一致。
- 新代码要带齐它依赖的 import 与配置；不要引入没人要求的依赖。
- 改完验证受影响的行为（配合 `verification-before-completion`）。
