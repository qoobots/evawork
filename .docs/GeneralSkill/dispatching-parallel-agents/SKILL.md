# 并行派发子代理

## 概述

有些任务可以同时做——**它们不碰同一批文件、不共享可变状态、彼此不依赖**。
这时串行做是在浪费时间。

**核心原则：独立性是前提，不是假设。**

## 何时用

**用**：2 个以上任务，且满足全部三条：
- 不修改**同一批文件**（不同模块/不同层）
- 不共享可变状态（同一份配置、同一把锁、同一个临时目录）
- **没有先后依赖**（B 不需要 A 的产出）

**不用**（这些情况串行才是对的）：
- 任务之间会**互相影响**（改同一处、改同一个接口）
- 有明确顺序（先定接口，再实现）
- **共享状态**（都要改同一个文件、都要写同一个目录）
- 任务很小（并行开销大于收益）
- 需要频繁交叉检查

⚠️ **判断标准是"会不会冲突"，不是"感觉能并行"。**
搞错的后果：两个子代理同时改一个文件，其中一个的改动被另一个覆盖，而且**很难发现**。

## 步骤

### 1. 识别独立域

列出所有待办，逐个判断：**它会碰哪些文件？和别的任务重叠吗？**

有重叠 → **合并成一个任务**或**串行**。

⚠️ 特别注意"看起来不重叠"的隐性共享：
- 都要改同一个配置文件（package.json、路由表、全局常量）
- 都要往同一个目录写产物
- 都要改公共类型定义（改一个类型会连带影响多个调用方）

### 2. 建聚焦的任务提示词

每个子代理的任务提示词要**自足**（它的上下文里没有你的历史）：

- 目标（一个可验证的产出）
- 确切文件路径
- 依赖的接口（确切签名）
- **明确的边界**：不许碰哪些文件
- 验证方式

⚠️ "改所有 X 相关的地方"这种提示词会让子代理扩散范围——写清确切路径。

### 3. 并行派发

一次性全部派出（`delegate` 可以并行调用），然后等全部回来。

⚠️ **本项目的限制**：子代理是 **never 档**，它们只能产出方案/补丁，不能直接落盘改文件。
所以这里的"并行"指的是**并行产出方案**，实际落盘由主任务统一做——
这恰好避免了并行写同一文件的风险。

### 4. 评审与整合

所有返回后：

1. **逐个核对**：它们有没有碰计划外的地方？有没有互相冲突的改动？
2. **落盘**：按任务合并成一个整体改动（主任务做）
3. **跑测试**：整体跑一次，确认并行改动**合起来**是通的
   ⚠️ 这一步不能省：每个子代理各自说"我这边没问题"，合起来仍可能冲突
4. 有冲突/覆盖 → 以**你（主任务）的判断**为准，别把冲突丢给用户

## 提示词结构

```
[任务目标]
[确切文件：新建 X、修改 Y]
[禁止触碰：Z、W]
[接口约定：...]
[验证方式：...]
```

## 常见错误

| 错误 | 后果 |
|---|---|
| 没检查文件重叠就并行 | 改动互相覆盖，且**可能静默丢失** |
| 提示词里没有"不许碰什么" | 子代理扩散范围，评审时才发现 |
| 并行做了有依赖关系的任务 | 后一个基于不存在的前提做 |
| 整合时不跑整体测试 | 单个都过、合起来不通 |
| 把并行当成默认 | 依赖任务并行 = 制造竞态 |
| 并行时用弱模型 | 省钱省在质量上 |

## 何时**不**该用（重要）

```
两条路之间拿不准 → 串行
```

并行是**优化**，正确性才是目标。
不确定是否会冲突时，串行做——慢一点总比丢改动好。

## 真实例子

```
任务清单：
 A. 改 /src/parser.ts 的解析逻辑
 B. 改 /src/render.ts 的渲染
 C. 加 /src/parser.test.ts

判断：
 A 与 B 文件不同 ✓
 A 与 C **碰同一个 parser** ✗ 有依赖

→ A 与 B 并行；C 等 A 完成后再做
```

## 验证

并行做完后，**必查三件事**：
1. 整体 diff：有没有计划外的改动
2. 有没有互相覆盖的痕迹（同一处改动出现两次）
3. 完整测试套通过

⚠️ 任何一条不过，就回到串行——**并行省下的时间不值得用风险换**。
